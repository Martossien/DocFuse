# DocFuse 0.2.2 beta — extraction deux fois plus rapide (pool de processus)

Version **correctif** : aucun changement d'API ni de format de corpus — la sortie est
strictement identique à la 0.2.1, fichier par fichier. Ce qui change : l'extraction
tourne dans un pool de **processus** au lieu de threads (D-111).

## Pourquoi

pdfminer, les parseurs XML et le rendu de pages sont du Python pur : sous le GIL,
huit threads ne valaient que 1,6 thread. Mesure du 02/09 sur 181 fichiers réels
(41 PDF, 12 Mo de texte extrait) :

| Exécution | Durée |
|---|---|
| 1 thread | 163 s |
| 8 threads (0.2.1) | 101 s |
| 8 processus (0.2.2) | **48 s** |

Le chemin critique reste le plus gros PDF (44 s d'OCR légitime) ; tout le reste se
range derrière.

## Comment

- Contexte `spawn` sur tous les systèmes (pypdfium2 déconseille `fork`), un seul pool
  par processus hôte, réutilisé d'un appel à l'autre — sous Windows un travailleur est
  un interpréteur à relancer, payé une fois par campagne, pas par lot.
- Ce que les threads donnaient gratuitement, refait entre processus : les journaux des
  travailleurs remontent au parent ; la borne du nombre de Tesseract simultanés
  (`OCR_MAX_CONCURRENCY`) vaut pour tout le pool via un sémaphore inter-processus ; la
  langue des messages voyage avec chaque tâche.
- Repli sur les threads, jamais d'échec : pool impossible à démarrer ou cassé en plein
  lot (aucun fichier perdu, ce qui n'était pas rendu est refait), exécutable gelé sur
  POSIX, ou `DOCFUSE_EXTRACTION_POOL=thread` pour forcer.
- `multiprocessing.freeze_support()` aux points d'entrée (`__main__`, `cli.main`,
  `gui.launch`), comme PyInstaller l'exige.

## Pour les intégrateurs

Rien à changer. Si votre application hôte est elle-même gelée avec PyInstaller,
appelez `multiprocessing.freeze_support()` en tête de votre point d'entrée (docia le
fait). Mémoire : ~100 Mo par processus une fois ses extracteurs chargés, 8 au plus.
